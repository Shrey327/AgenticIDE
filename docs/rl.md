# RL environments

The RL page supports tabular Q-learning and Stable-Baselines3 PPO/SAC: configure → train → inspect rewards and trace → compare held-out evaluation with random actions → inspect a seeded rollout → resume from a checkpoint. Runs use the project's configured Python, existing cancellation, and telemetry SDK. No model connection, paid account, GPU, network access, or added package is required for the built-in GridWorld environment.

## PPO and SAC

Create the RL template and run `uv sync --extra advanced --locked` to install its pinned optional environment. The lock uses the official CPU Torch index on Linux. Existing projects retain their package manager; install the documented pinned dependencies there and set that interpreter in Settings. **Recheck RL dependencies** reports installed package versions without installing anything.

Choose **PPO** for CartPole discrete actions or Pendulum continuous actions; **SAC** supports Pendulum. Configure training steps, one to four parallel environments, one to four distinct training seeds, and held-out evaluation episodes. With multiple workers, SB3 uses spawned environment processes, which are cancelled with the recorded job. Each environment is checked through SB3's environment checker. All neural training currently runs on CPU.

Each training seed receives an independent model. Held-out evaluation uses separate seed ranges and fresh environments, deterministic policy prediction, and no weight updates. The random-action baseline uses the same held-out episode seeds. The table reports mean return and, for multiple training seeds, standard deviation across their mean returns. This spread is not the variation between individual evaluation episodes; it is omitted for a single training seed. Per-seed summaries remain in `policy.json`. Pendulum has no success terminal, so return is shown without a fabricated success percentage. CartPole success means surviving the configured episode time limit; a shortened limit is not the official solved benchmark.

Checkpoints are saved periodically and at completion/cancellation. Select **Resume neural checkpoint** and keep the algorithm, environment, workers, training seeds, episode limit and learning rate unchanged. The requested steps are additional learning. Every resumed run writes a new policy directory. PPO optimizer state and SAC optimizer/entropy state and numeric replay buffer are restored; interrupted multi-seed experiments resume saved seeds and start any not yet visited. This is continuation of training, not a bit-for-bit restoration of simulator position or every random generator state.

Select a policy and run a held-out rollout. The step slider displays a CartPole/Pendulum state visualization, observations, actions and rewards. These are actual environment observations, without a render server or graphics dependency.

Neural checkpoints use SB3's ZIP export, but the IDE **never calls `SB3.load`** on user files: its metadata can contain cloudpickle. The runtime reconstructs only the two allowlisted built-in algorithms/architectures and loads expected tensor/optimizer members using `torch.load(weights_only=True)`, with bounded archives, path checks and SHA-256 verification. Torch **2.10.0 or newer** is enforced at runtime before neural training/loading; older releases are rejected because [CVE-2026-24747 affects `weights_only` loading through 2.9.1](https://github.com/pytorch/pytorch/security/advisories/GHSA-63cw-57p8-fm3p). SAC replay is numeric NPZ with `allow_pickle=False`; it is never loaded from pickle. Changing a saved artifact requires a new verified checkpoint. JSON provenance is not a defense against a malicious OS user editing the whole project, and host project code remains user-authorized code.

## Custom project environments

The RL template includes an editable `custom_target.py` example. After installing the advanced extra, open **Review a custom environment**, enter an ID/title, a workspace Python source, its factory function (default `make_env`), reviewed Python paths and a JSON parameter object. The factory receives that object and returns a `gymnasium.Env`. **Preview environment sources** reads text and hashes only; it never imports Python. Review each displayed file and the imports it uses, check the local execution authorization, then **Register reviewed environment**.

**Check environment (executes project Python)** imports the approved entrypoint and runs SB3's environment checker in a bounded helper. It reports the supported algorithms and observation/action spaces. Select the registered `custom:<id>` under **Neural environment** and use the ordinary PPO/SAC training, spawned workers, held-out/random evaluation, checkpoint/resume and rollout controls. Custom rollouts show the actual observation vector, actions and rewards without inventing a CartPole/Pendulum visualization. The generic success columns are omitted because custom environments need their own success definition; JSON episode summaries use the final `info.is_success` value when provided.

Supported custom observations are flat floating-point `Box` vectors with 1–256 components. PPO supports zero-based `Discrete(2–256)` or finite floating-point `Box(1–32)` actions. SAC requires that continuous Box. Every episode is wrapped with the configured time limit, retaining termination/truncation separately. Image/Dict/MultiDiscrete policies require a separate architecture adapter and are rejected. The default MLP architecture and tensor-only checkpoint loader remain fixed.

Up to 100 registration records live under `.aiide/rl-environments/`. Use distinct IDs for parameter variants when comparing policies. Each records the factory, JSON parameters and SHA-256 fingerprints for up to twenty listed UTF-8 Python files (256 KB/file, 1 MB combined); parameters are limited to 16 KB and ten nested levels. Parameters are retained in policy metadata; use project service environment variables for credentials. Symbolic links, named pipes, secret paths and workspace escapes are rejected. Source or settings changes during review invalidate registration. Before checking, training, creating worker/evaluation environments or rolling out a policy, the listed files must still match the approved revision. The entrypoint executes the bytes that were fingerprinted. Resume requires the same reviewed registration; after editing a factory, register the new revision and start a fresh policy. To use an older policy after changing its registration, restore the original files and registration settings, review them, and register that revision again.

Custom environments are **trusted local Python code with the user's account privileges**. Fingerprints detect changes to the listed files; they are not a sandbox or proof of safety. Installed dependencies, unlisted imported modules and external data still have normal Python access and are not frozen by a registration hash. Review imports and use the project lockfile. Shared bundles deliberately exclude registrations; recipients review and register their own sources. Checker/rollout helpers are cancelled and awaited on workspace shutdown. Bundled runtimes use an isolated launcher so workspace packages cannot shadow their safety checks; normal project imports become available only after custom-source review. External MCP agents cannot register/check custom factories or launch custom training, custom checkpoint resume or custom rollouts; those are explicit desktop actions. Built-in environment workflows retain their existing MCP scope.

Run `AIIDE_RL_TEST_PYTHON=/absolute/environment/bin/python node scripts/test-custom-rl.mjs` for actual custom PPO/SAC acceptance, including spawned workers, held-out improvement, telemetry, safe checkpoint/replay resume, rollout and changed-source rejection. `scripts/test-custom-rl-ui.mjs` uses actual Chrome components and the Workspace dispatcher for source review/consent → registration → Gym checker → training → rollout. On the included target example, the CPU regression runs achieved PPO return 9.1 versus random −5.83 and SAC 9.45 versus random 0.56. These are small seeded checks for the example, not evidence of arbitrary custom-task quality.

The factory contract follows [Gymnasium's custom environment guide](https://gymnasium.farama.org/introduction/create_custom_env/), and validation uses [SB3's environment checker](https://stable-baselines3.readthedocs.io/en/master/guide/custom_env.html).

## Using it

Create a **Local RL environment** project from Home, run its locked setup, and open **Train → RL environments**. Existing projects can use the same page with their Python executable configured in Settings.

Choose **Built-in GridWorld**, adjust the seed and episode count, and select **Train policy**. The default is 1,500 Q-learning episodes in a 5×5 grid. Starts are randomized; the bottom-right cell is the goal. The four actions are up, right, down, and left. A successful step earns +1; each other step costs −0.02. The configured slip probability replaces an action with a random action. Exploration decays to a floor of 0.01.

Alternatively install `gymnasium` with the project's existing package manager, then choose **Gymnasium FrozenLake-v1**. For this template use `uv add gymnasium`; other projects must use their existing manager. The adapter uses the standard slippery 4×4 map, its fixed starting cell, holes, rewards, and action ordering. GridWorld size and slip controls do not apply to FrozenLake. An absent package reports installation guidance in the run's diagnostics; it never silently chooses another environment.

Episode reward and length appear in the recorded experiment and ordinary Runs/Traces pages. Training is cancellable. Finished runs save a new `rl-policies/<id>/policy.json`; prior policies are never replaced. Select **Inspect policy**, enter an independent seed, and use **Run policy** to inspect each action and observation with the step slider. A hole is a terminal failure, not success.

## Reproducibility and safety

The training seed controls starts, transitions, and exploration. Evaluation uses a separate seed range and never updates weights. The same independent episode seeds are used for the learned policy and random-action baseline. Results measure this environment and seed set only. They are not evidence of generalization to unseen tasks.

Policies are JSON numeric Q tables, not executable Python or pickle files. Rollouts validate format, dimensions, finite values, file size, seed, and workspace containment; symbolic links are rejected by the core API. Configuration caps grid size, episodes, evaluation episodes, episode length, and the total training budget (two million steps). Training commands use the normal user-directed local run system. External agents need the existing explicit workflow permission to launch a run.

The page lists up to 300 policies. Training metrics are sampled to approximately 100 episodes per run to bound telemetry. Gymnasium's terminal and time-limit flags remain separate; Q-learning bootstraps at truncation and stops bootstrapping only at actual termination. Missing packages, malformed policies, and subprocess failures produce errors.

## Agent operations

- `rl.catalog`: environment descriptions, defaults, and limits.
- `rl.status`: advanced dependency availability, installed versions, and setup guidance.
- `rl.train`: validated tabular configuration or `{ "algorithm": "ppo", "environment": "CartPole-v1", "timesteps": 10000, "workers": 2, "seeds": [42, 43], "evalEpisodes": 10 }`; returns a recorded run. Inspect it with existing run/event tools and cancel through `runs.cancel`.
- `rl.policies`: bounded policy metadata and evaluation summaries; Q tables are excluded.
- `rl.rollout`: `{ "policy": "rl-policies/<id>", "seed": 12345 }`; returns bounded observations, actions, action labels, rewards, and terminal status.

## Scope and market comparison (2026-11-15)

The repository previously had supervised sweeps, PEFT text fine-tuning, evaluator rewards, and custom training jobs, but no explicit RL environment, learned policy artifact, separate evaluation seeds, or rollout viewer. It now supports the tabular starter and neural discrete/continuous control workflows.

[Gymnasium's API](https://gymnasium.farama.org/introduction/basic_usage/) is the reference for reset/step, explicit termination versus truncation, and standard environment interoperability. Its [FrozenLake documentation](https://gymnasium.farama.org/environments/toy_text/frozen_lake/) specifies the real environment used by the optional adapter. Those projects offer a broader environment ecosystem; this page exposes FrozenLake, CartPole, Pendulum and reviewed project factories alongside the dependency-free GridWorld starter.

[Stable-Baselines3's vector environment API](https://stable-baselines3.readthedocs.io/en/master/guide/vec_envs.html) documents the subprocess workers and reset/termination behavior used here. Its [save-format documentation](https://stable-baselines3.readthedocs.io/en/master/guide/save_format.html) explains why ordinary checkpoint metadata must not be deserialized from untrusted files. [Hugging Face TRL's GRPO trainer](https://huggingface.co/docs/trl/grpo_trainer) instead trains language models against sampled completions and rewards. The PPO in this IDE is environment-control PPO, not LLM PPO/GRPO or RLHF. Reviewed project factories are supported in this guide; robotics simulation, distributed GPU workers and language-model alignment remain separate work.

Run real advanced CPU acceptance with `AIIDE_RL_TEST_PYTHON=/absolute/environment/bin/python node scripts/test-advanced-rl.mjs` after building core/assets. It exercises the actual Workspace/Python/telemetry path plus real PPO with two spawned environments and multiple seeds, save/resume, protected checkpoint loading, and SAC continuous-action/replay continuation. The ordinary suite skips optional training acceptance when `AIIDE_REAL_RL=1` is absent; it does not report mock inference as real RL.

Real CPU validation on 16 November 2026 used SB3 2.7.1, Gymnasium 1.2.2, Torch 2.10.0 and Python 3.13.11. PPO trained for 8,000 requested steps per seed on CartPole (two training seeds, two subprocess environments, 200-step limit); held-out mean return was 188.9 versus a random baseline of 24.2 over ten evaluation episodes. SAC trained for 8,000 steps on Pendulum (one training seed, five held-out 200-step episodes); mean return was −463.42 versus random −988.91. These are included-environment regression checks, with explicit seeds and budgets, not solved-task or cross-hardware claims. Actual FrozenLake execution, neural checkpoint save/resume and optimizer/replay restoration also passed.

Validation covers deterministic training, held-out reward improvement, policy round-trip, explicit terminal/time-limit behavior, bounded input, corrupted Q tables, wrapper logging and cleanup, workspace path rejection, and optional real Gymnasium execution when installed. The built-in deterministic test reaches >95% success on its independent evaluation seeds and exceeds its random baseline by >0.5 mean reward. This is a regression assertion for the included GridWorld, not a market benchmark.
